# 在线作业系统测试执行台账设计

## 目标

为《软件设计实践》在线作业系统建立一份可由非专业测试人员逐项执行、记录证据并可回填到正式测试说明书的测试台账。测试覆盖课程考核要求中最关键的功能、安全和性能证据，不把尚未验证的历史测试结论当作本轮结果。

## 现状与边界

- 项目已有 4 个 `@SpringBootTest` Service 层测试类；当前没有 Controller/MockMvc 集成测试。
- 现有《软件测试说明书》包含历史版本的测试表和结论，其中部分环境、功能和性能数据与当前版本不一致，不能直接作为本轮的实测证据。
- 本轮首先产出 Markdown 执行台账，不修改正式 Word 测试说明书；待人工测试和截图完成后，再基于实际记录更新正式文档。
- 本轮手工测试以本地 MySQL + 浏览器前端为主。不会声称完成 HTTPS、OWASP ZAP、7×24 小时稳定性或 500 并发测试，除非后续实际执行并留下证据。

## 方案比较

1. 直接在 Word 测试说明书中填写：适合最终提交，但现场执行时表格编辑、截图命名和缺陷回填不便，且容易把历史结论与新结果混淆。
2. 单一 Markdown 执行台账：执行、勾选、截图命名和缺陷记录轻量，便于按真实结果逐项填充；完成后可整理为正式测试说明书。**本轮采用。**
3. 先做自动化 Controller 测试再做手工测试：证据质量高，但需要新增代码和调试环境，不适合本次由用户立即启动服务后进行截图的目标。

## 台账结构

1. 测试执行说明：环境、账号、启动前检查、截图和缺陷编号规则。
2. 自动化回归记录：运行现有 Maven 测试并记录真实控制台结果。
3. 手工功能用例：按管理员、教师、学生和端到端主流程分组；每条包含前置条件、操作、预期结果、实际结果和截图占位。
4. 安全用例：覆盖认证、角色隔离、资源越权、输入安全与上传限制；只列可在本地安全执行的验证。
5. 性能预备记录：先完成 JMeter 安装/脚本/单场景小并发试运行；最终性能指标仅由实际结果填写。
6. 缺陷与回归表：发现的问题统一编号，修复后记录回归结论和证据。

## 执行规则

- 仅将真实执行后的结果填为“通过”或“失败”；未执行保持“未执行”。
- 截图以 `TC-编号-序号-简述.png` 命名，例如 `FUNC-A01-01-admin-login.png`，并在用例中登记相对路径。
- 每个业务角色至少保留一张登录后首页截图；关键成功/拒绝流程各保留一张。
- 涉及新增、删除、转班、导入的用例使用明确的测试账号或测试数据，并在用例完成后记录清理情况，避免污染演示数据。
- 出现故障时，记录时间、操作、实际提示、截图/日志和影响范围；修复后在同一缺陷编号下添加回归结果。

## 验收标准

- 自动化回归、三角色主流程、关键权限边界和输入安全用例均有真实执行记录。
- 每个“通过”结论可追溯到截图、浏览器/控制台输出或导出文件。
- 未实际验证的项目保持未执行，不在正式文档中夸大为已通过。
- 记录完成后，测试结果可直接转换为正式《软件测试说明书》的测试环境、用例、缺陷与总结章节。
